# SupportPilot RAG 检索阈值标定实验报告

> 结构化索引与复现入口见 [`OPTIMIZATION_GUIDE.md`](OPTIMIZATION_GUIDE.md)。
> 实验日期：2026-09-29  
> 实验环境：Python 3.12.14 / BAAI/bge-small-zh-v1.5 / ChromaDB 1.5.9 / 知识库 21 chunks  
> 复现基线：官方 `evals/run_rag_eval.py` → Top1 100% (4/4)、Recall@3 100%、No-answer 100% (1/1)、Quality Gate PASS  
> 结论一句话：**官方"拒答准确率 100%"是 1 个用例的运气；把阈值从 0.70 调到 0.50，域外漏过从 6/8（75%）降到 0/8，域内 10/10 零误杀。更关键的是：官方那 5 条评测集对这个参数完全无感（0.40~0.70 全部 100%），只有扩展集才能看见差异。另外，这次实验里我推翻了自己的一条用例标注（域内/域外分错组）——见 3.6。**

## 〇、指标口径（先对齐名词，后面反复用）

| 指标                    | 定义                                                                  | 大白话         |
| --------------------- | ------------------------------------------------------------------- | ----------- |
| **Top1 准确率**          | 检索结果**第 1 条**的 `source` 等于标准答案的用例比例                                 | 第一个拿出来的对不对  |
| **Recall@3**          | 检索结果**前 3 条**中任意一条 `source` 等于标准答案的用例比例（命中即可，不论排名）                  | 前三本里有没有对的那本 |
| **No-answer 准确率（拒答）** | `expected_source: null` 的用例中，`top1_source is None`（**一条都不返回**）的用例比例 | 该没依据时有没有真闭嘴 |

> 判定来源：`evals/run_rag_eval.py`。Top1 / Recall@3 只在**正样本**（`expected_source` 非 null）上算；拒答准确率只在**拒答用例**上算，且判定极严——**必须一条都检索不到才算成功**，返回任何一条（哪怕距离很远）都算失败。

## 一、实验动机

复现官方评测时，5 个用例全部 PASS，包括那唯一一个拒答用例。但我在手工抽查时发现，**同一个问题换个说法，就立刻失效了**：

| 提问                | 来源       |    top1 距离 | 是否被拒答            |
| ----------------- | -------- | ---------: | ---------------- |
| 你们公司**创始人**是谁？    | 官方拒答用例   |     0.7424 | ✅ 被拦（> 0.70）     |
| 你们公司 **CEO** 是谁  | 我加的同义改写  | **0.6307** | ❌ **漏过**（< 0.70） |
| 你们公司**股票代码**是多少   | 我加的同类新问题 |     0.6396 | ❌ 漏过（< 0.70）     |

**「创始人是谁」和「CEO 是谁」问的是同一件事**（公司领导人信息，知识库里都没有），只是换了种说法，距离就从 0.7424 掉到 0.6307，**跨过 0.70 这条线，从"拦得住"变成"漏过"**。「股票代码」是同一档（看似业务、库里没有）里的另一个新问题，同样漏过。

> 这里要分清两种失效，面试时常被追问：
> - **同一意图的不同表达失效**（创始人 → CEO）→ 说明模型对**措辞敏感**，阈值余量不足；
> - **同类意图的不同问题失效**（创始人 → 股票代码）→ 说明**覆盖面不足**，这一档问题整体拦不住。
> 两者都指向同一个结论：`0.70` 这道线的位置不对。

这说明：`MAX_DISTANCE = 0.7` 这道"及格线"的余量极其有限，**官方评测 100% 通过并不代表拒答能力成立**。于是设计本实验，把这个问题量化。

> 注：`retriever.py` 的判定逻辑是 `passed = distance <= MAX_DISTANCE`，距离越小表示语义越相关。评测脚本对拒答用例的判定是 `top1_source is None`——**必须一条都检索不到才算拒答成功**。

## 二、实验方法

1. **构造两组问题**
   - **域内组（10 条）**：真实业务问题，含"退款/退换货/物流/会员"四类，且刻意混入口语化改写（如"钱什么时候退回来""我那个耳机不想要了还能退吗""金卡有什么用"）来模拟真实用户表达。最后 1 条 `我听说你们退款要30天是真的吗` 是**前提错误型**（库里有退款政策、只是用户把数字记错），它按"库里有没有依据"应归域内，详见 3.6
   - **域外组（8 条）**：知识库中确实**没有依据**的问题，细分两档
     - 完全无关（4 条）：`北京到上海高铁要多久`、`帮我写一首关于春天的诗`、`苹果手机怎么关机`、`今天天气怎么样`
     - 看似业务但库里没有（4 条）：`你们公司股票代码是多少`、`你们CEO是谁`、`你们公司创始人是谁？`、`你们的竞品是哪家公司`
2. **关闭过滤拿原始距离**：把 `MAX_DISTANCE` 临时设为 99，使 `search_knowledge_base()` 返回全部 top3 及各自距离，不受阈值干扰
   - ⚠️ 这一步是**必须**的：带着阈值跑，那些距离超过阈值的域外问题会直接被过滤掉（返回 0 条），**你只会看到"无结果"，却不知道它们的距离是多少**，域外分布的上界和分母都会丢
3. **统计每个候选阈值下的拦截效果**：
   - **域外漏过** = 域外问题的 top1 距离 ≤ 阈值的条数（漏过越多越差）
   - **域内误杀** = 域内问题的 top1 距离 > 阈值的条数（误杀越少越好）

实验脚本见 `evals/probe_threshold.py`（拿原始距离 + 输出标定表），对照测试集固化在 `evals/rag_cases_hard.jsonl`（域内 10 条 + 域外 8 条，含难度分档 `tier` 字段）。

两点值得注意：

### 3.3 两组的分离边界

```
0.00   0.2548 ──────────── 域内区间 ──────────── 0.4438
                                                    ↓ 空隙 0.1252（宽裕）
0.5690 ────────────── 域外区间 ────────────── 0.7690
                                    0.70（旧阈值，太靠右）
                       0.50（新阈值，落在空隙内）
```

**域内上界 0.4438 与域外下界 0.5690 之间有 0.1252 的空隙**——两类问题的距离分布**干净地分离**，中间留出了足够宽的可用区间。这正是"存在明确最优阈值"的证据：不是靠猜，而是量出来的。

> ⚠️ **反过来说，这一步的真正意义是"可行性判断"，不只是"取数"**：如果两组分布**重叠**（域内也有 0.6 的、域外也有 0.3 的），那就说明**阈值这条路根本走不通**，必须换方案（换 embedding 模型 / 加 rerank / 改判定逻辑）。做阈值标定前必须先证实"分布可分"。
>
> 空隙中间点 = (0.4438 + 0.5690) / 2 = **0.5064**，所以取 0.50 时两侧余量最均衡（to 域内 0.0562 / to 域外 0.0690）。

### 3.5 阈值扫描：改这个参数，官方评测会不会跟着动？

为了回答"改了 `MAX_DISTANCE`，那些指标到底会不会变"，我写了 `evals/threshold_sweep.py`，把阈值从 0.40 到 0.70 逐个跑一遍，官方评测集和扩展集各跑一次。

**官方评测集（5 条，决定 Quality Gate 是否 PASS）**

| 阈值   | Top1 准确率     | Recall@3     | 拒答准确率 (no-answer) |
| ---- | ------------ | ------------ | ----------------- |
| 0.40 | 4/4 = 100.0% | 4/4 = 100.0% | 1/1 = 100.0%      |
| 0.45 | 4/4 = 100.0% | 4/4 = 100.0% | 1/1 = 100.0%      |
| 0.50 | 4/4 = 100.0% | 4/4 = 100.0% | 1/1 = 100.0%      |
| 0.55 | 4/4 = 100.0% | 4/4 = 100.0% | 1/1 = 100.0%      |
| 0.60 | 4/4 = 100.0% | 4/4 = 100.0% | 1/1 = 100.0%      |
| 0.70 | 4/4 = 100.0% | 4/4 = 100.0% | 1/1 = 100.0%      |

**扩展集（我构造的域内 10 条 + 域外 8 条）**

| 阈值   | 域内 10 条命中 | 域外 8 条漏过 |
| ---- | --------- | -------- |
| 0.40 | 6/10      | 0/8      |
| 0.45 | 10/10     | 0/8      |
| 0.50 | 10/10     | 0/8      |
| 0.55 | 10/10     | 0/8      |
| 0.60 | 10/10     | 2/8      |
| 0.70 | 10/10     | 6/8      |

**两个关键发现：**

1. **官方 5 条评测集对这个参数完全无感。** 从 0.40 到 0.70，三个指标全部 100%、一动不动。原因是它的 4 条正样本距离都远小于 0.40（落在 0.25~0.35 一档），而唯一那条拒答用例距离高达 0.7424，无论阈值落在 0.40~0.70 的哪一点都拦得住。**换句话说，如果只跑官方评测，你永远发现不了 0.70 有问题**——这正是它"粉饰太平"的机制，也是我一开始被 100% 误导的原因。
2. **0.50 的推荐依据是"离两侧悬崖都远"，不是"它分数最高"。** 0.45 / 0.50 / 0.55 三个值结果完全相同（域内 10/10、域外 0/8），**不存在谁更优**；差别只在**安全边际**：0.45 距 0.40 那条"开始误杀"的下降沿（0.40 时域内掉到 6/10）只有 0.05，而 0.50 距空隙中点 0.5064 最近，两侧余量最均衡（to 域内 0.0562 / to 域外 0.0690）。真实业务问题的分布比这 18 条更宽，取 0.50 更稳。

> ⚠️ **别把"空隙宽裕"误读成"可以随便取"。** 0.45~0.55 只是**在这 18 条上**表现相同；真实业务问题的距离分布会更宽（会有比 0.4438 更啰嗦的真实提问），所以按"离下降沿最远"来选，而不是按"底线能压多低"来选。
>
> 运行方式：`./.venv/Scripts/python.exe evals/threshold_sweep.py`（在哪个目录下跑都可以；脚本只在内存里临时改 `MAX_DISTANCE`，不改动任何项目文件）。

### 3.7 对照集扩充后的复核（18 → 25 条）

`OPT-011` 把对照集扩充到 **25 条**（域内 17 + 域外 8），补上多意图混合、超短问句、政策口径冲突三类真实表达。**重跑标定后，结论有重要变化。**

| 指标 | 扩充前（18 条） | 扩充后（25 条） |
|---|---|---|
| 域内上界 | 0.4438 | **0.4652**（+0.0214） |
| 域外下界 | 0.5690 | 0.5690（不变） |
| 分离空隙 | 0.1252 | **0.1038** |
| 阈值 **0.45** 的域内误杀 | 0/10 | **2/17** |
| 阈值 **0.50** 的域内误杀 | 0/10 | **0/17** |
| 阈值 **0.50** 的域外漏过 | 0/8 | **0/8** |

**两个结论：**

1. **`0.50` 仍然有效**（域内 17/17 命中、域外 0/8 漏过、官方集回归 4/4 + 4/4 + 1/1 仍 PASS）→ **不需要改代码**。
2. **但它的性质变了**：扩充前 `0.45 / 0.50 / 0.55` 三值同分，`0.50` 处在"可用区间中点"；扩充后 **`0.45` 开始误杀（2/17）**，可用窗口收窄为 **`0.50 ~ 0.55`**，`0.50` 从"中点"变成了**区间下沿**。

> ★ **这一条比数字本身更值钱**：`0.45` 从"零误杀"变成"误杀两条"，唯一的变量是**测试集变强了**（多了一条约 0.4652 的超短问句「多久到」）。
> 也就是说 —— **参数的"余量"是测试集给的，不是参数自带的**。用弱测试集定参数，等于用一把刻度不准的尺子去量长度。

> ⚠️ 另记录一处"标注前的实测纠正"：「我买的会员退款是不是更快」原推测命中 `membership_policy.txt`，**实测是 `refund_policy.txt`（0.3705）**。
> 若凭感觉填 `expected_source`，这条会被判成"错命中"，把整份数据污染掉 —— 这正是 3.6 节那次标注错误的翻版，也是新建 `evals/inspect_query.py` 存在的理由。

## 四、结论

1. **原阈值 0.70 明显偏松。** 它在 8 条域外问题上只拦掉 2 条（25%），拒答能力实质上不成立。官方 No-answer 100% 的成绩，来自**唯一一个用例恰好落在 0.7424、刚好超过阈值 0.04 的侥幸**。
2. **推荐取 0.50。** 域外漏过从 6/8 降到 0/8，域内误杀保持 0/10，**零召回损失换取 6 条域外拦截**。
3. **可用区间 0.45~0.55，工程上落一个 0.50。** 该区间内三个取值结果完全一致，说明结论不敏感于区间内的具体取值；取 0.50 的理由是**它最接近两类分布空隙的中点 0.5064，两侧缓冲最均衡**。⚠️ **注意：这是"单点值"的候选区间，代码里只能写一个数**，不存在"把 `MAX_DISTANCE` 设成 0.45~0.55 这种区间"的写法。
4. **不要低于 0.45。** 0.40 时域内误杀已经升到 4/10，会开始伤害真实业务问答，是比"漏答"更严重的故障。
5. **这一条不该被"拦"——它是域内问题，缺口在生成层**（详见 3.6）。"我听说你们退款要30天是真的吗"实测 top1 就是 `refund_policy.txt`（0.4438），**检索层正确命中了它**。它需要的能力不是"更严的阈值"，而是**把检索到的原文和用户的前提做比对**：政策原文写"银行卡退款 3 至 7 个工作日"，用户说 30 天，模型应当**指出前提冲突并给出正确数字**。这是分层认知：**检索层负责"有没有依据"，生成层负责"依据是否支持这个说法"**。把它当成检索层的漏网之鱼，是**用错了尺子**——距离量的是话题相关度，不是主张真伪。
6. **评测指标要选对"体检项目"。** 官方 5 条评测集对 `MAX_DISTANCE` 完全不敏感（0.40~0.70 全部 100%），说明**评测集的覆盖度决定了你能发现什么问题**。一个只在"容易样本"上跑通 100% 的评测，会把参数缺陷完全掩盖。这是本实验最大的方法论收获：**指标绿了不等于系统好了，得先确认这套指标"有没有能力变红"。**

### 3.6 一条自我纠错：为什么这条用例的归属被我改过

这是整个实验里**唯一一次我推翻自己**，也是面试时最能体现"残差分析"的地方，单独记一节。

**最初**，`我听说你们退款要30天是真的吗` 被我放进了**域外组**（`expected_source: null`，即"应该拒答"）。理由是它属于"对抗性/错误前提"样本。

**复核发现问题**：这条问题问的是"退款到底几天"，而知识库里**确实有** `refund_policy.txt`。实测它的 top1 就是 `refund_policy.txt`，距离 0.4438 —— **检索层完全正确地命中了它，它没有失败。**

**改判**：把它移回**域内组**（`expected_source: "refund_policy.txt"`，tier 改为 `in_domain_wrong_premise`）。判据很硬：**域内/域外的划分标准是"知识库里有没有依据"，不是"用户的说法对不对"。** 用户把数字记错，不改变"这个话题在库里有依据"这个事实。

**改判带来三个连锁结论**：

1. **检索层其实是干净的。** 域内上界 0.4438、域外下界 0.5690，**两组的分离空隙从"0.0059"变成"0.1252"** —— 原来的"缝隙极窄"是**标注错误造成的假象**。修正后，"存在明确最优阈值"这个结论反而更硬了。
2. **0.50 之后，真正该拦的 8 条域外问题全部拦住了（0/8 漏过）**，不存在"残余漏网之鱼"。
3. **真正的缺口在生成层**：用户说 30 天、原文说 3~7 个工作日，模型需要**识别并纠正前提冲突**。

> **定量说明为什么阈值救不了它**：若坚持用阈值把它当"该拒答"拦掉，可用窗口只有 `[0.4379, 0.4438)`，**宽 0.0059** —— 而 0.40 时真实业务问题已经误杀 4/10。窗口窄到不可用，**证明这条不是"参数没调好"，而是"工具选错了"**。
>
> **正确做法**：这条应该由**生成层**处理 —— 在 prompt 中要求"回答必须引用政策原文的数字；若用户陈述与原文冲突，先指出冲突再给正确数字"，或在答案生成后加一道**答后校验**（把答案里的数字与召回的原文比对，不一致则重生成）。**它也不该留在检索评测里**，因为 `run_rag_eval.py` 只看检索结果、看不出"模型有没有被错误前提带跑"——那是另一层评测该干的事。

## 五、建议的落地改动

```python
# src/supportpilot/rag/retriever.py
# MAX_DISTANCE = 0.7      # 旧值：域外漏过 6/8（75%）
MAX_DISTANCE = 0.50       # 新值：域外漏过 0/8，域内误杀 0/10（推荐值，单点值非区间）
```

**改完必须做的事（否则等于没验证）**：

1. 重跑 `python evals/run_rag_eval.py`，确认 Top1 / Recall@3 / No-answer 仍 PASS（实测：4/4、4/4、1/1，因为域内上界 0.4438 < 0.50）
2. 把 18 条对照题通过 `evals/rag_cases_hard.jsonl` 固化（已完成），并复制 `run_rag_eval.py` 为 `run_rag_eval_hard.py` 让两套集走**同一套指标口径**，把官方集与扩展集的两列数字并排进报告
3. 观察 No-answer Accuracy 的真实数字（官方 1 条仍是 100%，**扩展集上才看得到真水平**）

> ⚠️ **这里的"指标下降"是好事。** 它意味着你终于测出了真实水平，而不是被一个用例粉饰过的 100%。面试时这正是加分项。
>
> ⚠️ 但注意：**"改完阈值就万事大吉"是错的**。3.6 那条前提错误用例证明了检索层有明确边界，**生成层的前提校验是另一个待补的缺口**（项目当前没有答案质量层的评测）。

## 六、可写进简历的表述

> 在复现基线评测（5 用例全 PASS）基础上进行批判性复核，发现拒答能力的成立依赖单一用例的偶然性：将拒答问题同义改写后，检索距离由 0.7424 降至 0.6307，直接越过 0.70 阈值导致漏答。
>
> 据此设计阈值标定实验：先临时关闭距离过滤以获取不受阈值污染的原始距离，再构造域内 10 条（含 3 条口语化改写、1 条前提错误）与域外 8 条（完全无关 / 看似业务但缺失两档）对照集。量化距离分布后发现域内上界 0.4438 与域外下界 0.5690 之间存在 0.1252 的干净分离空隙，据此完成 0.40~0.70 全阈值扫描，将 `MAX_DISTANCE` 由 0.70 调整为 0.50（贴近空隙中点、离两侧误杀/漏过悬崖最远），**域外漏过由 6/8（75%）降至 0/8，域内召回零损失（10/10）**。
>
> 过程中另获两项方法论产出：① 发现官方 5 条评测集对该参数**完全不敏感**（0.40~0.70 三指标恒定 100%），即"评测全绿"不等于"参数正确"，据此补齐了评测集的灵敏度盲区；② 通过残差复核**推翻了自己对一条用例的组别标注** —— 「我听说你们退款要30天是真的吗」原被归为"应拒答"，复核后确认其话题在库内（top1 命中 `refund_policy.txt`，0.4438），应为域内用例。进一步量化证明：若要用阈值拦住它，可用窗口仅 `[0.4379, 0.4438)`、宽 0.0059，而 0.40 时真实问题已误杀 4/10 —— 因此该类"错误前提"问题在检索层无解，需在生成层通过 prompt 约束核对政策原文数字，形成**"检索层管有无依据、生成层管依据是否支持该说法"的职责分层**。
